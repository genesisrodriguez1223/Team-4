# Playbook v0.1 — Working Agreement

Team 4 (Gabriel Cruz, Madison Galloway, Genesis Rodriguez, James Lee)

## 1. Branching strategy

Trunk-based, branch-per-feature, or something else — and the rule for how long a branch may live before it merges.

Team 4 will be using the trunk-based branch strategy. A high level of integration will be used. There will be small changes, real tests, hours low.. Etc. The branch will live for 2-3 weeks before it merges.

## 2. Definition of done

What must be true before a piece of work is finished. Not “it works” — the actual checklist.

The definition of done for team 4 is if we perform the action that made the website go down, will it work as intended? If it didn’t cause the website to go down. The team will repeat the action that originally caused the website to go down and confirm that the issue no longer occurs.

*Considered done when:*

 - [ ]The action that originally caused the website to go down has been tested again.
 - [ ]The website remains running after this action is made.
 - [ ]The feature or action works as intended.
 - [ ]No new errors or bugs are introduced.
 - [ ]The changes have been reviewed by the team.
 - [ ]All required approvals have been received.
 - [ ]The changes have been successfully merged into the teams main branch.

## 3. Sprint length and the cadence of your ceremonies

Team 4’s sprint length will be done biweekly. The cadence of our ceremonies will be done twice a week.

## 4. Pull requests and review rules

Who reviews, how many approvals, what a reviewer is expected to check, and what happens when a review stalls.

Team 4’s pull request and review process will be done by Genesis Rodriguez. There will be three approvals needed. Reviewers are expected to examine the submitted changes, including the code, data, and API-related work. If a review stalls, the review will be reassigned to another team member to collaborate on the issue.

# 2. Prompt-Log policy: 
What gets logged: 

 In the creation of our team application, there may be a point where AI models might be used to generate code to serve as reference on what the next steps should be. Because of the use of AI, any prompts input by the developers must be logged alongside the generated code to show which parts of the application made use of it. Alongside logging the input/output results from the AI conversation, any modified code as well as the time the modifications took place must also be recorded. 

Where the information is stored: 

The best way for the team to store the documented information from both developer modifications, as well as any AI generated content, is to keep them within the programming repository, in this case, GitHub. Here the repository will keep track of any logged information and is able to be easily accessed by all team members 

Who is reasonable: 

For the application to be able to be developed with little to no conflict, it is the responsibility of each team member; to log any information they wish to upload and/or change into the repository. It is also the job of the respective team members to review their work prior to uploading to ensure that they are following any rules and expectations set by the team leader. 

 

# 3.Rules for AI-Assisted code review: 

 Prior to the team coming in to review and change any errors in the code, the AI will begin a check-up to ensure any obvious errors have not been looked past and corrected. The changed code from the AI will then be sent for review and will run through the initial developer. After any major changes have been made, it is then sent to be reviewed by three other members of the team to approve the changes and finally be sent to be uploaded to the main branch
